# 圖譜 Schema 定義與遍歷／聚合 Trace 範例

對應決賽交付內容第 4 項：「系統功能說明（含 graph schema 定義與遍歷/聚合 trace 範例）」。

本文件描述**使用者—職缺互動圖**（Interaction Graph）之結構與推論時之查詢方式。
實作位於 `src/graph_builder.py`（建構）與 `src/graph_ranker.py`（遍歷與聚合）。

> 命題允許參賽者自行設計圖譜結構：「圖譜之具體結構（節點與邊之定義、是否帶權重等）由參賽者自行設計」。
> 本圖以行為訊號為邊，用於協同過濾排序。

---

## 1. Schema 定義

### 1.1 圖型別

有向圖（`networkx.DiGraph`），單一邊方向：`User → Job`。
無 Job → User 邊；反向查詢透過 `G.predecessors(job_node)` 完成。

### 1.2 節點

| 節點型別 | 節點 ID 格式 | 屬性 | 型別 | 說明 |
|---------|-------------|------|------|------|
| `User` | `user:{talentNo}` | `node_type` | `str` | 固定為 `"User"` |
| | | `talentNo` | `int` | 求職者編號 |
| `Job` | `job:{職缺編號}` | `node_type` | `str` | 固定為 `"Job"` |
| | | `job_id` | `int` | 職缺編號（`職缺.csv` 主鍵） |
| | | `city` | `str` | 工作城市，缺值為 `""` |
| | | `category_mid` | `str` | 職務中類，缺值為 `""` |

**節點納入條件**

- `User`：`talentNo ≠ 0` 且非空。`talentNo = 0` 代表匿名／無法識別，多列不得視為同一人，故一律排除。
- `Job`：至少存在一筆互動事件。無人瀏覽或應徵之職缺不建立節點（不影響其被檢索，僅不參與圖排序）。

### 1.3 邊

| 屬性 | 型別 | 說明 |
|------|------|------|
| `weight` | `int` | 同一 `(user, job)` 對之所有互動事件權重總和 |

**邊權重定義**

| 事件型別 | 來源 | 權重 |
|---------|------|------|
| `apply`（主動應徵） | `主動應徵_0601-0607.csv` | **3** |
| `view`（職缺瀏覽） | `職缺瀏覽_20260601_20260607.csv` | **1** |

同一 `(user, job)` 對之多次事件累加為單一邊：

```
weight(u, j) = 3 × |{u 對 j 的應徵事件}| + 1 × |{u 對 j 的瀏覽事件}|
```

權重比例 3:1 之依據：應徵為較強之正向訊號（工作坊簡報明列「職缺瀏覽（弱）」／「主動應徵（強）」），且應徵行為需付出額外成本，受曝光位置偏差之影響顯著小於瀏覽。

### 1.4 規模

| 指標 | 數值 |
|------|------|
| 節點總數 | 約 441,000 |
| 邊總數 | 約 3,200,000 |
| 來源事件數 | 5,091,661（已排除 `talentNo = 0`） |
| 建構時間 | 約 4–5 分鐘（首次） |
| 序列化快取 | `dataset/graph_cache.pkl`，載入約 5 秒 |

### 1.5 防洩漏

依命題規定，圖譜僅得使用 train 期資料建構。評測時：

- 事件僅取 `2026-06-01 ~ 2026-06-05`
- 職缺文字以 `職缺最後修改時間 < 2026-06-06` 過濾（`職缺.csv` 無上架時間欄位，此為代理條件）

## 2. 推論時之遍歷與聚合

圖譜於推論時**不重建**，僅查詢。兩種模式依使用者狀態分派。

### 2.1 模式 A — 登入使用者：兩跳協同過濾

**輸入**：`talent_no`、第二階段檢索產生之候選職缺 ID 集合 `C`
**輸出**：`job_id → graph_score` 之對應表

```
步驟 1  種子職缺
        seeds = G.successors("user:{talent_no}")
        若 |seeds| > 50，取 edge weight 最大之前 50 筆（限制展開扇出）

步驟 2  共同使用者（反向遍歷）
        for each seed in seeds:
            co_users = G.predecessors(seed)  排除自己、僅取 node_type == "User"
            每個 seed 最多取 30 位（限制展開扇出）

步驟 3  共同使用者的其他職缺（正向遍歷）
        for each co_user:
            for each co_job in G.successors(co_user):
                跳過 co_job ∈ seeds（使用者已互動過）

步驟 4  聚合
        若 co_job 之 job_id ∈ C：
            graph_score[job_id] += weight(co_user, seed) × weight(co_user, co_job)
```

聚合語意：*共同使用者對種子職缺的黏著度* × *該使用者對候選職缺的黏著度*。
兩者皆高時貢獻最大 —— 即「與你行為高度重疊的人，也高度投入的職缺」。

**扇出上限**：`MAX_SEED_JOBS = 50`、`MAX_CO_USERS_PER_JOB = 30`，最壞情況下的遍歷量為
`50 × 30 × avg_out_degree`，確保單次查詢延遲有界（實測 10–100 ms）。

### 2.2 模式 B — 匿名使用者：加權入度聚合

官方 API 合約不含 `talentNo`，評測時一律走此路徑。

```
for each job_id in C:
    jnode = "job:{job_id}"
    若 jnode ∉ G：略過
    graph_score[job_id] = Σ over p in G.predecessors(jnode) of weight(p, jnode)
```

即該職缺在圖上之**加權入度**。相較於原始瀏覽次數，此訊號
(a) 僅計入可識別之登入使用者，(b) 對應徵給予 3 倍權重。

### 2.3 分數融合

兩種模式共用同一融合公式：

```
final_score = (graph_score / max_graph_score) × 0.7
            + (popularity  / max_popularity)  × 0.3
```

正規化以候選集合內之最大值為分母，避免不同量級之分數相互淹沒。
若圖譜未提供任何訊號（`graph_score` 全為空），退回純熱門度排序。

## 3. Trace 範例

### 3.1 模式 A — 兩跳協同過濾

情境：`talent_no = 138`，查詢「台北 前端工程師」，第二階段回傳 1,008 筆候選。

```
起點  user:138
      │
      ├─[weight=4]─▶ job:77037910   (台中市 / 業務推廣)      ← 種子 1
      ├─[weight=1]─▶ job:81244501   (台中市 / 行政後勤／總務)  ← 種子 2
      └─[weight=3]─▶ job:79115320   (台中市 / 財務會計)      ← 種子 3
                     （共 9 筆事件，取全部作為種子，未達 50 上限）

反向遍歷 job:77037910 的 predecessors（最多 30 位）
      │
      ├─ user:452118  ─[weight=3]─▶ job:77037910
      │                └─正向─▶ job:88012455  [weight=6]   ← 在候選集合 C 內 ✓
      │                └─正向─▶ job:90773011  [weight=1]   ← 不在 C，略過
      │
      └─ user:983204  ─[weight=1]─▶ job:77037910
                       └─正向─▶ job:88012455  [weight=2]   ← 在 C 內 ✓

聚合
      graph_score[88012455] = (3 × 6)   ← 經由 user:452118
                            + (1 × 2)   ← 經由 user:983204
                            = 20

融合（假設本次候選集合中 max_graph = 20、max_pop = 850，
      job 88012455 之 popularity = 612）

      final = (20 / 20) × 0.7 + (612 / 850) × 0.3
            = 0.700 + 0.216
            = 0.916
```

> 上述節點編號為結構示意。實際數值依 `graph_cache.pkl` 建構結果而定，
> 可執行 `python -m src.graph_builder` 後以 `src/graph_ranker.py` 之
> `_get_graph_scores()` 重現。

### 3.2 模式 B — 加權入度聚合

情境：匿名查詢「台北 前端工程師」，候選集合含 `job:113124505`。

```
反向遍歷 job:113124505 的 predecessors

      user:200341 ─[weight=3]─┐            （1 次應徵）
      user:551027 ─[weight=1]─┤
      user:773915 ─[weight=2]─┼─▶ job:113124505
      user:889201 ─[weight=1]─┤
      user:990113 ─[weight=1]─┘

聚合  graph_score[113124505] = 3 + 1 + 2 + 1 + 1 = 8
      （加權入度：5 位使用者、其中 1 位投遞履歷）

對照  原始瀏覽次數 = 7（含匿名瀏覽，且不區分應徵）
      圖譜訊號較能反映「可識別使用者的真實投入程度」
```

## 4. 與技能圖譜之關係

命題描述之核心生成式 AI 模組為**技能圖譜**（由 LLM 自職缺文字萃取技能、正規化同義詞、判斷關聯）。
本文件所述之互動圖為**行為協同過濾圖**，二者為不同層次、可並存：

| | 互動圖（本文件） | 技能圖譜 |
|---|---|---|
| 節點 | 使用者、職缺 | 技能 |
| 邊來源 | 行為紀錄 | LLM 自職缺文字萃取 |
| 解決的問題 | 排序階段的個人化 | **檢索階段的召回率** |
| 冷啟動 | 無效（圖上無邊） | 有效（技能可跨職缺泛化） |

離線評測顯示，本系統之主要失分來自**檢索階段召回不足**（相關職缺僅 27.9% 進入候選集合），
此為技能圖譜之目標區間；互動圖則作用於其後之排序階段。
兩者之量化貢獻請參見 `eval/ABLATION_REPORT.md`。
