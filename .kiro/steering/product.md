# Product Overview

A job recommendation API that returns the top 10 most relevant job listings for a given user search query. Deployed as a FastAPI service on AWS EC2, containerised with Docker.

## Core Goal

Given a user's search query (and optionally city/category filters), surface and rank the 10 best-matching job listings from ~1,000,000 job listings. Supports anonymous and authenticated users with different ranking strategies.

## API Endpoints

| Method | Path | Description |
|--------|------|-------------|
| POST | `/api/v1/jobs/search` | Official competition endpoint — accepts `query`, `location_code`, `duty_code`; returns `request_id` + ranked `[{job_id, rank}]` |
| POST | `/recommend` | Detailed debug endpoint — accepts `query`, `talent_no`, `c0`, `d0`; returns full job dicts |
| GET | `/health` | Health check |
| GET | `/debug/db-status` | DuckDB table row counts and sample data |

## Three-Stage Pipeline

```
User query (str) + optional c0/d0 filters
     ↓
querytoRequirement()   — Bedrock Claude semantic parsing → tags list
     ↓
grabFromDatabase()     — semantic expansion + DuckDB SQL filter + JOIN popularity score
     ↓
ranking()              — popularity / personalised / graph-based (configurable)
     ↓
Top 10 job listings
```

### Stage 1 — Semantic Analysis (`querytoRequirement`)
- Rule-based abbreviation expansion first (pt→兼職, BE→後端工程師, FE→前端工程師, etc.)
- Bedrock Claude LLM parses expanded query into structured tags
- Semantic expansion for category/brand words (速食→麥當勞,肯德基,...; 便利商店→7-11,全家,...)
- Specific job titles preserved as-is (前端工程師, 軟體工程師)
- City normalisation (台北→台北市) and salary parsing (35k以上→薪資>=35000)
- LRU cache (256 entries) avoids repeated API calls
- Fallback to whitespace tokenisation after 3 failed LLM attempts

### Stage 2 — Retrieval (`grabFromDatabase`)
- Semantic expansion via `職務對照表.CodeAlike` (e.g. 軟體工程師 ↔ 軟體設計師)
- Optional c0/d0 code resolution (numeric codes → Chinese city/category names)
- DuckDB SQL filter on `職缺.csv` (~1M rows) for speed
- JOIN `瀏覽次數.csv` to attach popularity score
- Attaches `relevance_hits` count (how many search terms each job matched)

### Stage 3 — Ranking (`ranking`)

Four ranking paths, selected by configuration and user state:

1. **Anonymous + popularity** (`talentNo = 0`, default):
   - Sort by `relevance_hits` → `score` → `職缺最後修改時間`

2. **Anonymous + graph** (`talentNo = 0`, `GRAPH_FOR_ANONYMOUS_USER=true`):
   - Graph-degree scoring via NetworkX/Neptune

3. **Authenticated + personalised** (`talentNo ≠ 0`, normal user):
   - `final_score = personal_score × 0.7 + normalised_popularity × 0.3`
   - `personal_score` = location_match × 0.4 + category_match × 0.4 + salary_match × 0.2
   - Primary sort by `relevance_hits`, secondary by `final_score`

4. **Authenticated + graph** (`talentNo ≠ 0`, `GRAPH_FOR_SIGNED_IN_USER=true`):
   - Graph-based collaborative filtering (skill overlap, co-user signals, city match)
   - Falls back to feature-based or popularity if Neptune/NetworkX unavailable

5. **Cold-start** (`total_events < 3`): falls back to popularity ranking

## Graph RAG (Optional Enhancement)

Knowledge graph built from user behaviour + job attributes:
- **Vertices**: User, Job, Skill, City, Category
- **Edges**: VIEWED (user→job), APPLIED (user→job), REQUIRES (job→skill), LOCATED_IN (job→city)
- **Ranking signals**: skill overlap between user history and candidate jobs, co-user collaborative filtering, city preference matching
- **Implementation**: NetworkX (local, pickle-cached) or Amazon Neptune (remote, Gremlin queries)
- Skills extracted from job titles/content via structured rules + optional LLM

## User Behaviour Data

Two derived tables pre-generated by `userAnalysis.py`:

- **`userBehaviorFeature.csv`** — one row per authenticated user; fast lookup for personalised ranking
- **`userBehaviorEvents.csv`** — full event log; used for graph building and evaluation

Anonymous rows (`talentNo = 0`) are excluded from both tables.

## Target Users

Job seekers on a job platform. Users may be:
- **Anonymous** (`talentNo = 0`): no personalisation, popularity-based or graph-degree ranking
- **Authenticated** (`talentNo ≠ 0`): personalised ranking based on view/apply history
  - **Cold-start**: fewer than 3 historical events → treated same as anonymous

## Deployment

- **Runtime**: Docker container on AWS EC2 (t3.large, 8 GB RAM)
- **Port**: 8000
- **Infrastructure**: CloudFormation stack (EC2 + security group)
- **Current endpoint**: `http://35.85.148.23:8000`

## Evaluation

Offline evaluation framework in `eval/` with:
- Test set generation from held-out user interactions
- Metrics: NDCG, MRR, Hit@K
- Ablation studies comparing popularity vs personalised vs graph ranking
- Stratified analysis by user activity level
