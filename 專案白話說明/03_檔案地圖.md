## `src/` — 核心程式碼（★ 全部都重要）

| 檔案 | 白話說明 |
|------|---------|
| ★ `pipeline.py` | **總指揮**。只有 40 行，就是「呼叫階段1 → 階段2 → 階段3」。想看全貌從這裡開始 |

| ★ `ranker.py` | **階段 3：排序**。決定走熱門度排序、個人化排序、還是圖譜排序 |
| ☆ `graph_builder.py` | 用 networkx 建「使用者→職缺」圖譜，存成快取檔。**預設不執行** |
| ☆ `graph_ranker.py` | 圖譜版的排序邏輯（兩跳協同過濾）。**預設不執行** |

## `eval/` — 離線評測框架（★ 全新，命題交付第 6 項）

**這整個資料夾在做一件事：幫你們的搜尋引擎「打分數」。**

命題規定評審會親手執行參賽者提供的評分腳本，來驗證「生成式 AI 是不是必要環節」。這 20% 的分數就是這樣評的。

### 程式（跑的順序就是這個順序）

| 檔案 | 白話說明 |
|------|---------|
| ★ `reproduce.sh` | **評審只要跑這一支就好**。它會自動建環境、產資料、跑評測、出報告 |
| ★ `build_testset.py` | **出考題 + 印答案卷**。從 06/06 的真實搜尋抽 500 題，用「使用者搜尋後點了什麼／投了什麼」當標準答案 |
| ★ `build_popularity.py` | 算職缺熱門度，**但只用訓練期（06/01–06/05）的資料** —— 防止系統偷看考試當天的答案 |
| ★ `build_graph_train.py` | **建圖譜，一樣只用訓練期資料**。產出使用者—職缺互動圖（41 萬節點、256 萬條邊） |
| ★ `metrics.py` | **閱卷規則**（NDCG@10、Hit@1、Hit@10…）。裡面有 9 項手算驗證，因為指標算錯的話後面所有數字都是廢的 |
| ★ `run_ablation.py` | **閱卷機**。把同一批考題餵給七種不同設定（開 AI／關 AI／開圖譜／關圖譜…），各自算分 |
| ☆ `analyze_strata.py` | 把 500 題拆成「短關鍵字」和「長查詢」分開算，並做統計顯著性檢定 |
| ☆ `graph_ranker_interaction.py` | 互動圖譜的排序邏輯（評測專用，不影響線上服務） |

### 報告（給評審看的）

| 檔案 | 內容 |
|------|------|
| ★ `EVALUATION_REPORT.md` | **量出了什麼** —— 結果表、兩層診斷、建議行動 |
| ★ `EXPERIMENT_DESIGN.md` | **為什麼這樣量** —— 時序切分、標註規則、防洩漏設計、已知弱點 |
| ★ `README.md` | 怎麼跑、每個檔案幹嘛 |
| ☆ `STRATIFIED_HYBRID.md` | 分層比較 + 顯著性檢定的結果 |
| ☆ `NEW_*.md` / `NEW_*.json` | 各次實驗的原始輸出 |
| ☆ `testset.jsonl` | 500 題考題與答案（320KB，刻意上傳讓評審能驗證我們的數字） |

### 三個最重要的觀念

**1. 時間切分（防作弊）**
```
06-01 ~ 06-05  訓練期 ── 系統只能看這段
06-06          考題 ──── 從這天抽 500 個真實搜尋
06-06 ~ 06-07  答案 ──── 只用來看「使用者後來點了什麼」
```

**2. 為什麼要「有 AI / 沒 AI」各跑一次**
命題明講：如果拿掉生成式 AI 分數沒差，就當作 AI 是裝飾品、大幅扣分。所以要自己證明拿掉會變差。

**3. 我們誠實回報了負面結果**
實測是「拿掉 AI 反而好一點」，但差異未達統計顯著，而且診斷出兩個原因。詳見 [08_評測結果與應對.md](08_評測結果與應對.md)。
