# 01 · 三分鐘搞懂這個專案

## 一、這是什麼比賽

**2026 雲湧智生：臺灣生成式 AI 應用黑客松競賽**，命題單位是 **1111 人力銀行**。

主辦方給了六份真實資料（一週份，2026/06/01–06/07）：

1. `職缺.csv` — 約 100 萬筆職缺（標題、內容、薪資、地點、分類…）
2. `職缺瀏覽` — 誰看了哪個職缺（約 840 萬筆）
3. `主動應徵` — 誰投了哪個職缺（比「看過」更強的訊號）
4. `userSearchLog` — 誰搜了什麼關鍵字、當時看到哪些結果
5. `城市對照表` — 地區代碼 ↔ 地區名稱
6. `職務對照表` — 職務代碼 ↔ 職務名稱，還有「相似職稱」欄位

**要做的東西**：一個搜尋排序引擎。
評審會用一批保密的查詢，打我們的 API，看我們回傳的前 10 名職缺準不準。

**怎麼算分**（都在看「前排準不準」）：

| 指標 | 白話意思 |
|------|---------|
| NDCG@10 | 前 10 名排得好不好，越相關的越前面分數越高 |
| Hit@1 / Top-1 | 第一名有沒有猜對 |
| Hit@10 / Precision@10 | 前 10 名裡有幾個是對的 |
| MRR | 第一個正確答案排在多前面 |

**評分比重**：創意 25% ／ 技術可行性 25% ／ 商業應用 20% ／ **主題切合度 20%** ／ 完成度 10%
（另外用 AWS Kiro 開發可加 5% — 我們有用，`.kiro/` 資料夾就是證據）

## 二、我們做了什麼

一句話：**「AI 讀懂你的話 → 快速撈出候選 → 智慧排序」三段式流水線（Pipeline）。**

```
使用者打字：「台北 前端工程師 35k以上」
        │
   ┌────▼────────────────────────────────┐
   │ 階段 1：AI 語意解析                  │
   │ 用 AWS Bedrock 上的 Claude 模型      │
   │ 把白話文翻成標籤：                    │
   │ ["前端工程師", "台北市", "薪資>=35000"] │
   └────┬────────────────────────────────┘
        │
   ┌────▼────────────────────────────────┐
   │ 階段 2：從 100 萬筆撈候選             │
   │ 用 DuckDB 下 SQL 過濾                │
   │ 加上「相似職稱擴展」                  │
   │ → 剩下約 1000 筆候選                 │
   └────┬────────────────────────────────┘
        │
   ┌────▼────────────────────────────────┐
   │ 階段 3：排序                         │
   │ 依「熱門度 + 個人偏好」算分           │
   │ → 取前 10 名                         │
   └────┬────────────────────────────────┘
        │
   回傳：前 10 筆職缺編號 + 名次
```

**速度**：整個流程約 1～3.5 秒，瓶頸在階段 1 呼叫 AI（1～3 秒）。
階段 2 只要 50～200 毫秒，階段 3 不到 10 毫秒。

## 三、三個「我們比較特別」的地方（上台可以講的亮點）

### 亮點 1：AI 負責「聽懂人話」，規則負責「不出錯」

一般的搜尋是關鍵字硬比對，使用者打「pt」就找不到「兼職」的職缺。
我們做了兩層：

- **規則層**：13 組縮寫對照表寫死（pt→兼職、fe→前端工程師、be→後端工程師、devops→開發維運工程師…），這層不會失敗
- **AI 層**：交給 Claude 處理規則沒涵蓋的口語，例如「月薪4萬」→「薪資>=40000」

如果 AI 掛掉或回傳格式錯誤，會**重試 3 次**，還是不行就退回純規則模式 —— 服務不會整個死掉。
這叫「優雅降級（graceful degradation）」，是評審會欣賞的工程細節。

### 亮點 2：熱門度用「時間衰退」算，不是單純數次數

如果只數瀏覽次數，一個上架三個月的老職缺會永遠霸榜。
我們的公式：

```
熱門分數 = Σ [ e^(-0.1 × 距今天數) × 事件權重 ]
                                    應徵 = 3 分
                                    瀏覽 = 1 分
```

白話：**「越近期的互動越值錢，7 天前的互動只剩一半價值；投履歷比只是點進去看重要 3 倍。」**

### 亮點 3：有圖譜 / 無圖譜雙軌，一個開關切換

我們用 networkx 建了一張「使用者 ↔ 職缺」互動圖譜
（**44.1 萬個節點、320 萬條連線**），可以做「跟你行為相似的人還看了什麼」這種協同過濾推薦。

但**預設是關閉的**，因為：

1. 只有一週資料，互動太稀疏，圖的效果不穩
2. 21.8%（36,174 / 166,539）的使用者是冷啟動（行為少於 3 筆），圖上根本沒東西可查
3. 圖載入要吃 500MB 記憶體、開機多花 5 秒

改 `.env` 裡兩個環境變數就能開關，不用改一行程式碼。
這剛好對應命題要求的「有圖譜 vs 無圖譜 ablation（消融實驗）」。

## 四、部署在哪裡

- **AWS EC2**（t3.large，2 核心 8GB 記憶體，Amazon Linux 2023）
- 用 **CloudFormation** 一鍵開機器（`infra/cloudformation.yaml`）
- 用 **FastAPI + Uvicorn** 跑 API
- AI 模型用 **AWS Bedrock** 上的 Claude 3.5 Sonnet
- 也有寫好 `Dockerfile`，要容器化也可以

**公開網址**：`http://35.85.148.23:8000`
**Swagger 互動文件**：`http://35.85.148.23:8000/docs` ← 現場 demo 直接開這個最快
