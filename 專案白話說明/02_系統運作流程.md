# 02 · 系統運作流程（逐步拆解）

這份文件跟著一次真實的搜尋走一遍，讓你知道每一秒鐘系統在做什麼。

**情境**：使用者在搜尋框打了「**台北後端 pt工作 薪水35k以上**」

---

## 事前準備：離線 ETL（比賽前就跑完的資料前處理）

在使用者搜尋之前，我們已經先把原始資料「嚼過一遍」，做出三張衍生表。
這些是離線跑的（跑一次要幾分鐘），線上查詢時直接讀現成結果，所以很快。

### 衍生表 1：`瀏覽次數.csv`（職缺熱門度）— 由 `dataset/genViewCount.py` 產生

把 840 萬筆瀏覽 + 應徵紀錄，壓縮成每個職缺一個「熱門分數」。

```
熱門分數 = Σ [ e^(-0.1 × 距今天數) × 權重 ]     應徵=3 分、瀏覽=1 分
```

- 產出 **288,319 筆**（有被互動過的職缺）
- 欄位：職缺編號、瀏覽次數、主動應徵次數、score

### 衍生表 2：`userBehaviorFeature.csv`（使用者偏好卡）— 由 `dataset/userAnalysis.py` 產生

每個登入使用者一列，記錄他的口味：

| 欄位 | 意思 |
|------|------|
| `preferred_city_1/2/3` | 最常看／投的前 3 個城市 |
| `preferred_category_1/2/3` | 最常看／投的前 3 個職務中類 |
| `salary_floor` | 他投過的職缺薪資下限的第 25 百分位（= 他大概不接受低於這個數字） |
| `total_events` | 總共有幾次行為 |
| `is_cold_start` | 行為 < 3 次就標記為「冷啟動」（資料不足，別亂猜） |

- 產出 **166,539 位使用者**，其中 36,174 位（21.8%）是冷啟動
- ⚠️ `talentNo = 0`（未登入）的紀錄全部排除，因為那不是同一個人

### 衍生表 3：`userBehaviorEvents.csv`（行為明細）

每一次瀏覽／應徵一列，共 **5,091,661 筆**。用來建圖譜，也用來 debug 時看「這個人最近在看什麼」。

### （選用）衍生表 4：`graph_cache.pkl`（圖譜快取）

用 networkx 建的「使用者 → 職缺」有向圖，44.1 萬節點、320 萬條邊。
第一次建要 4–5 分鐘，之後存成檔案，載入只要 5 秒。**預設不載入。**

## 階段 1：AI 語意解析 — `src/query_parser.py`

**輸入**：`"台北後端 pt工作 薪水35k以上"`
**輸出**：`["後端工程師", "台北市", "兼職", "薪資>=35000"]`

### 1-1. 縮寫展開（規則式，0 毫秒）

`src/utils/abbreviations.py` 裡有 13 組寫死的對照：

| 縮寫 | 展開 | 縮寫 | 展開 |
|------|------|------|------|
| pt | 兼職 | be | 後端工程師 |
| ft | 全職 | fe | 前端工程師 |
| ui | 介面設計師 | ml | 機器學習工程師 |
| ue | 使用者體驗設計師 | ai | 人工智慧 |
| rd | 研發工程師 | pm | 產品經理 |
| qa | 品質保證工程師 | hr | 人力資源 |
| devops | 開發維運工程師 | | |

聰明的地方：`pt工作` 這種「英文縮寫黏中文」也能拆 → 變成 `兼職`
（「工作」被判定為無意義的雜訊詞，直接丟掉）

### 1-2. 呼叫 AI（AWS Bedrock + Claude Sonnet 4.6，約 2 秒）

> **⚠️ 2026-08-01 晚間更新**：模型換了、prompt 也大幅升級。

丟一段 system prompt 給 Claude，要求它只回傳 JSON 字串陣列。prompt 現在做四件事：

| 功能 | 例子 |
|---|---|
| 翻譯 | `software engineer` → 軟體工程師 |
| 地點正規化 | 台北 / Taipei → 台北市 |
| 薪資格式統一 | 35k以上 → 薪資>=35000、月薪4萬 → 薪資>=40000 |
| **知識型語意擴展** | **速食 → 麥當勞、肯德基、漢堡王、摩斯、頂呱呱** |

最後一項是規則式永遠做不到的 —— 你不可能把全台灣的品牌名寫死在對照表裡。這是 LLM 帶進來的世界知識。

其他例子：便利商店 → 7-11／全家／萊爾富；手搖 → 五十嵐／清心／迷客夏；咖啡 → 星巴克／路易莎／cama。

> **但要注意**：離線評測顯示這個擴展是雙面刃 —— 它提升召回率，卻會犧牲前排精確度。
> 詳見 [08_評測結果與應對.md](08_評測結果與應對.md)。

### 1-3. 檢查 + 重試 + 保底

- 檢查 AI 回的東西是不是「一個純字串的陣列」
- 格式不對就**重試，最多 3 次**
- 3 次都失敗 → **退回用空白切字**（`"台北 後端"` → `["台北", "後端"]`）

👉 **這是重點**：AI 掛掉服務不會死，只是變笨一點。延遲反而變成 <10 毫秒。

### 1-4. 後處理（正規化）

即使 AI 回得不完美，程式還會再修一次：
「台北」→「台北市」、「35k以上」→「薪資>=35000」、「35000以上」→「薪資>=35000」

## 階段 2：撈候選職缺 — `src/retriever.py`

**輸入**：標籤清單 + 選填的地區代碼(c0)、職務代碼(d0)
**輸出**：約 1000 筆候選職缺（每筆都帶著熱門分數）
**耗時**：50～200 毫秒

### 2-1. 標籤分類（`src/utils/tag_parser.py`）

把一堆標籤分成四類：

```
["後端工程師", "台北市", "兼職", "薪資>=35000"]
        ↓
  cities     = ["台北市"]        ← 比對城市對照表
  salary_min = 35000             ← 抓「薪資>=數字」
  job_types  = ["兼職"]          ← 全職/兼職/工讀/中高階/其他
  job_terms  = ["後端工程師"]     ← 剩下的當職稱關鍵字
```

### 2-2. 相似職稱擴展（Semantic Expansion）

這是**提升命中率的關鍵一步**。

`職務對照表.csv` 有個 `CodeAlike` 欄位，裡面是主辦方整理的相似職稱。
搜「後端工程師」時，我們順便把 `CodeAlike` 裡的相關寫法一起撈出來
（例如 Backend、伺服器端工程師、Server 端…）。

👉 上台可以講：**「同一個技能有很多寫法，我們用官方對照表做同義詞擴展，
避免使用者打『Backend』就漏掉寫『後端工程師』的職缺。」**

### 2-3. 用 DuckDB 下 SQL 撈資料

DuckDB 可以**直接對 CSV 檔案下 SQL**，不用先匯入資料庫、不用架伺服器。
100 萬列的 CSV 也是毫秒級。

實際跑的 SQL 長這樣（簡化版）：

```sql
SELECT j.*, COALESCE(p.score, 0.0) AS score
FROM '職缺.csv' j
LEFT JOIN '瀏覽次數.csv' p ON j.職缺編號 = p.職缺編號
WHERE j.工作城市 IN ('台北市')
  AND j.薪資下限 >= 35000
  AND j.職缺屬性 IN ('兼職')
  AND (j.職務名稱 ILIKE '%後端工程師%' OR j.職務名稱 ILIKE '%Backend%' OR ...)
```

`LEFT JOIN 瀏覽次數.csv` 這一步就是把**熱門分數黏上去**，
排序階段直接用，不用再算一次。

### 2-4. 代碼篩選（c0 / d0）

評審打 API 時可能會附上地區代碼、職務代碼：

- `c0=["100100"]` → 查城市對照表 → 「台北市」→ 加進城市條件
- `d0=["140214"]` → 查職務對照表 → 對應的職務小類名稱 → 加進條件

⚠️ 程式裡的規則：**如果有 d0，就不套用職稱模糊比對**（因為 d0 是精確分類，比關鍵字猜測準）。

## 階段 3：排序 — `src/ranker.py`

**輸入**：約 1000 筆候選
**輸出**：前 10 名
**耗時**：< 10 毫秒

排序會走哪條路，看使用者是誰：

```
候選是空的？ ────────────────→ 回傳空陣列
        │
        ▼
talentNo = 0（匿名）？ ───────→ 【路線 A】純熱門度排序
        │                        （如果開了匿名圖譜開關 → 走圖譜 degree 排序）
        ▼
有開圖譜開關？ ───────────────→ 【路線 C】圖譜協同過濾
        │
        ▼
查不到偏好卡 / 冷啟動？ ───────→ 【路線 A】純熱門度排序
        │
        ▼
                                【路線 B】個人化排序
```

### 路線 A：相關性優先排序（匿名／冷啟動用）

> **⚠️ 2026-08-01 晚間更新**：這一段的邏輯被改過了，以下是最新版本。

排序鍵有三層，由左到右依序比較：

```python
(relevance_hits, score, 職缺最後修改時間)
  ↑命中幾個搜尋詞  ↑熱門度  ↑新鮮度
```

**先看相關性** —— 命中越多搜尋詞的職缺排越前面；相關性相同才比熱門度，再相同才比新鮮度。

`relevance_hits` 是階段 2 的 SQL 新增的欄位，計算每筆職缺命中了幾個查詢詞。

#### 為什麼這個改動很重要

改之前的排序鍵只有 `(score, 職缺最後修改時間)` —— **完全不看相關性**，查詢字串只用來過濾，通過過濾的候選一律視為同等相關，然後純粹挑最熱門的 10 筆。

離線評測抓到的實例：

```
搜尋「會計」
  改版前： 早班門市 / 賣場營運服務專員 / 工讀活動指導專員   ❌
  改版後： 會計 / 行政會計人員 / 門市行政會計助理           ✅
```

### 路線 B：個人化排序（登入且有足夠行為）

```
最終分數 = 個人分數 × 0.7 + 熱門度 × 0.3

個人分數 = 地點是否命中偏好 × 0.4
         + 職類是否命中偏好 × 0.4
         + 薪資是否達到門檻 × 0.2
```

每一項就是「中了給 1 分、沒中給 0 分」，很直白。
（薪資如果沒資料，給 0.5 分，不獎不罰）

熱門度會先除以全體最高分做正規化（壓到 0～1），才不會蓋過個人分數。

👉 **這個公式的可解釋性很高**，評審問「為什麼這筆排第一」，你可以直接算給他看。

### 路線 C：圖譜協同過濾（`src/graph_ranker.py`，預設關閉）

登入使用者的兩跳（2-hop）走訪：

```
你 ──看過／投過──→ 職缺 A、職缺 B
                      │
              其他也看過 A 的人（最多取 30 人）
                      │
              他們還看過職缺 X、Y、Z
                      │
              X/Y/Z 如果在候選名單裡 → 加分
```

加分公式：`那個人對 A 的黏著度 × 那個人對 X 的黏著度`，累加起來。
最後一樣混合：`圖譜分數 × 0.7 + 熱門度 × 0.3`。

匿名使用者也有圖譜版本：算每個候選職缺的「加權入度」
（= 所有登入使用者對它的互動總權重），等於一個更乾淨的熱門度訊號
（只算登入使用者、且投履歷算 3 倍）。

**任何一步失敗（圖沒建、記憶體不夠、查不到），都會自動退回熱門度排序。**

## 出口：API 回傳 — `app.py` / `api.py`

線上部署的版本提供三個端點：

| 端點 | 用途 |
|------|------|
| `POST /api/v1/jobs/search` | **官方比賽格式**（評審打這個） |
| `POST /recommend` | 完整職缺資訊（自己 debug 用，會回傳職務內容全文） |
| `GET /health` | 健康檢查，回 `{"status": "ok"}` |

官方格式的輸入輸出：

```jsonc
// 請求
{
  "query": "台北 前端工程師",          // 必填
  "location_code": ["100100"],        // 選填，地區代碼
  "duty_code": []                     // 選填，職務代碼
}

// 回應
{
  "request_id": "req_1686a745",
  "result": [
    {"job_id": "113124505", "rank": 1},
    {"job_id": "98863698",  "rank": 2},
    ...共 10 筆
  ]
}
```

規則：rank 從 1 開始連續、不重複、越小越前面、找不到就回空陣列 `[]`。
