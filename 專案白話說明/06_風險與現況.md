## 🔴 風險 1：我們的圖譜「不是命題要的技能圖譜」

### 事實

命題文件寫得很明確：

> **AI 技能圖譜建構（生成式 AI 核心模組）**：運用 LLM 由職缺文字中萃取技能、
> 正規化同義詞、進行分類，並判斷技能間之關聯關係，建構為結構化之技能圖譜。
> …須於提案中明確展示推論時對結構之查詢、遍歷或聚合使用方式，
> 並提供 **graph schema 定義**與**至少一個遍歷/聚合 trace 範例**。

我們實作的是：**使用者 → 職缺的互動圖**（協同過濾用），
節點是「人」和「職缺」，不是「技能」。
而且 LLM 完全沒有參與建圖 —— 圖是從行為紀錄直接統計出來的。

### 為什麼危險

「主題切合度」佔 **20%**，驗證方式白紙黑字寫著：

> 若移除生成式 AI 模組後核心指標 NDCG@10 無顯著退化，
> 則視為生成式 AI 非必要環節，**本項分數將大幅扣減**。

我們的 LLM 只做查詢解析，而且**有規則式 fallback**。
如果評審把 LLM 關掉跑 ablation，很可能發現分數差不多 —— 這正是命題要抓的情況。

### 怎麼應對

1. **不要迴避，主動說明取捨**（Q2 的答法在 [05_上台報告腳本.md](05_上台報告腳本.md)）
2. 強調 `CodeAlike` 同義詞擴展 = 一個**現成的、零幻覺的職務關聯圖**，
   我們選擇用它取代 LLM 萃取，理由是可靠性
3. 說明技能圖譜是規劃中的下一步，且架構已經預留接口
4. **今晚如果還有時間** → 見下方「今晚最值得補的東西」

## 🔴 風險 2：交付清單有兩項還沒做

命題的「決賽交付內容」第 6 項要求：

> GitHub 連結：含完整原始碼、README（須涵蓋環境設定、執行範例、
> **benchmark 重現步驟**、**random seed 與資料/模型/索引版本說明**）、
> 依賴版本鎖定檔，以及「**有圖譜 vs 無圖譜」雙重指標 ablation script
> （須能一鍵重現，供評審統一執行驗證主題切合度）**。

| 項目 | 狀態 |
|------|------|
| 完整原始碼 | ✅ 有 |
| README 環境設定 | ✅ 有 |
| README 執行範例 | ✅ 有 |
| README benchmark 重現步驟 | ⚠️ 有寫「怎麼跑」，但**沒有實際分數** |
| 資料/模型/索引版本說明 | ✅ 有（README 有專章） |
| random seed 說明 | ❌ **沒有** |
| requirements.txt 版本鎖定 | ✅ 有 |
| **一鍵 ablation script** | ❌ **沒有** |
| **NDCG@10 vs baseline 的實測改善數字** | ❌ **沒有** |

另外「效果標準」要求：

> 排序結果於 hold-out 評估集之 NDCG@10 須較 baseline 有可量化提升
> （建議相對改善幅度 ≥ 5% 為佳）；Hit@1、Hit@10 須同步報告，
> 並於 README 標註是否採用 position bias correction。

我們目前**沒有任何實測指標數字**。

### 怎麼應對

- 被問到就誠實說「時間限制下沒完成，這是我們清楚的缺口」
- **絕對不要編造 NDCG 數字** —— 評審會實際跑腳本驗證
- 把重點放在**架構完整度、工程穩健性、可解釋性**這些我們真的做得好的地方

## 🟠 風險 3：線上跑的程式碼，跟 GitHub 上的不一樣

### 事實（我今天實測發現的）

| | git repo 裡的 `app.py` | 線上伺服器實際跑的 |
|---|---|---|
| 端點 | `POST /search` | `POST /api/v1/jobs/search` |
| 輸入欄位 | `ks`, `c0`, `d0`, `talentNo` | `query`, `location_code`, `duty_code` |
| 輸出欄位 | `rank`, `empStr` | `request_id`, `result[{job_id, rank}]` |

**線上版本是對的**（符合工作坊簡報公告的合約），
**但那份程式碼沒有 commit 進 git**。

我實測 `POST /search` 打線上伺服器 → 回 `{"detail":"Not Found"}`，
證實線上跑的不是 repo 裡這份。

### 為什麼危險

命題要求交 GitHub 連結含「完整原始碼」。
如果評審 clone 下來跑，會發現端點對不上他們的測試腳本。

### 怎麼應對

**今晚務必找隊友把伺服器上的版本 commit 回 git。** 兩個做法：

```bash
# 做法 A：從伺服器把檔案抓回來
scp -i your-key.pem ec2-user@35.85.148.23:~/recommendation-algorithm/app.py ./app.py
git add app.py && git commit -m "sync deployed API contract"

# 做法 B：問隊友是不是有沒 push 的分支
git fetch --all && git log --all --oneline
```

## 🟠 風險 4：AWS 憑證會過期

`.env` 裡用的是 `AWS_SESSION_TOKEN`（臨時憑證），
`deploy.md` 自己也寫了：

> **AWS Session Token 過期**：如果用臨時憑證，記得定期更新 `.env` 中的 token 並重啟服務

### 如果過期會怎樣

不會整個掛掉 —— 會**靜默降級**：
LLM 呼叫失敗 → 重試 3 次（每次都失敗）→ 退回空白分詞。

搜「台北 前端工程師」還是會有結果（因為空白分詞剛好夠用），
但搜「月薪四萬的兼職」這種口語查詢就會爛掉，
而且**你不會收到任何錯誤訊息**，只會覺得結果怪怪的。

### 怎麼應對

- **上台前 30 分鐘，用一個「需要 AI 才解得出來」的查詢測試**：
  ```bash
  curl -X POST http://35.85.148.23:8000/api/v1/jobs/search \
    -H "Content-Type: application/json" \
    -d '{"query": "月薪四萬以上的台北兼職"}'
  ```
  如果回的結果明顯不合理（沒過濾薪資、沒過濾兼職），八成是憑證過期了
- 請隊友準備好備用憑證和重啟指令

## 🟡 風險 5：正式評測時，個人化排序不會生效

工作坊 FAQ 明確寫：

> talentNo 能個人化？ **正式 payload 沒有 talentNo，線上 API 不應依賴。**

所以評審打 `/api/v1/jobs/search` 時，`talent_no` 一律是 0 → 走匿名路徑
→ **實際被評分的排序邏輯只有「條件過濾 + 時間衰退熱門度」**。

那套漂亮的個人化公式（0.4/0.4/0.2）和圖譜協同過濾，在正式評分中完全不會被執行。

### 怎麼應對

- 這不是 bug，是規則使然。**誠實說明**（Q6 的答法）
- 把個人化定位成「為 1111 實際產品情境準備的能力」，
  在 `/recommend` 端點示範，講商業價值時很有力
- **但要意識到**：我們真正在拚分數的，是熱門度排序的品質

## 🟡 風險 6：你這台電腦跑不起來（衍生資料缺檔）

`dataset/` 目前**缺這四個檔案**：

- `瀏覽次數.csv`（排序要用）
- `userBehaviorFeature.csv`（個人化要用）
- `userBehaviorEvents.csv`（建圖要用）
- `graph_cache.pkl`（圖譜要用）

要生出來得跑（會花幾分鐘到幾十分鐘）：

```bash
python dataset/genViewCount.py
python dataset/userAnalysis.py
python -m src.graph_builder      # 選用，4-5 分鐘
```

**線上伺服器上有這些檔案，所以 demo 是正常的。**
但如果你打算在自己筆電上現場跑 `main.py`，會失敗。

👉 **建議：明天現場一律用線上 API demo，不要在筆電上跑。**

## 🟡 風險 7：兩個 API 主程式並存，容易搞混

根目錄同時有 `app.py` 和 `api.py`，功能重疊。
差別是 `api.py` 開機時會**無條件載入圖譜**（吃 500MB + 5 秒），
`app.py` 只有開關打開時才載入。

評審看 repo 可能會問「到底哪個是主程式」。

**答法**：「`app.py` 是正式服務入口，`api.py` 是早期開發版本，
差別在資源預載策略；正式部署跑的是 app 這條線。」

## 🟢 小問題（提一下，不影響評分）

- `src/graph_builder.py` 和 `src/graph_ranker.py` 是 **UTF-16 編碼**（其他檔案都是 UTF-8）。
  程式能跑，但在某些編輯器裡開會看到亂碼。不用今晚處理。
- `main.py` 裡的範例呼叫是直接寫在檔案最外層（不在 `if __name__ == "__main__":` 裡），
  所以 `import main` 就會執行。只影響 debug 便利性。
- `check_cities.py` 是一次性的檢查腳本，可以不用管。

## 今晚最值得補的三件事（依 CP 值排序）

### 1️⃣ 把線上版本的程式碼 commit 回 git（10 分鐘，必做）

風險 3。這是**最低成本、最高風險移除**的一件事。

### 2️⃣ 寫一個 ablation script（1–2 小時，如果隊友還有力氣）

不用做到完美，做出一個 `run_ablation.py`，能：

- 讀一批查詢（可以從 `userSearchLog` 抽 100 筆有 `empStr` 的）
- 分別在「LLM 開 / LLM 關（純規則）」、「圖譜開 / 圖譜關」四種組合下跑
- 用 `empStr` 裡使用者實際點過/投過的職缺當作 relevance label
- 算出 NDCG@10 / Hit@1 / Hit@10 印成一張表

**就算數字不好看，有這張表 = 交付項目有交，比完全沒有好太多。**
命題原文是「須能一鍵重現，供評審統一執行」—— 重點是「能跑」。

### 3️⃣ 在 README 加一段「Random Seed 與 Position Bias 說明」（10 分鐘）

命題點名要的兩件事，寫清楚就好，不用做到：

```markdown
## Random Seed
本系統的檢索與排序流程為完全確定性（deterministic），
不含隨機取樣、隨機初始化或隨機打散步驟，因此無需設定 random seed。
唯一的非確定性來源為 LLM 生成（temperature 由 Bedrock 預設值控制），
已透過 JSON schema 驗證 + 最多 3 次重試 + 規則式 fallback 收斂輸出空間。

## Position Bias Correction
本系統**未採用** IPS 或 Doubly Robust 等曝光偏差修正方法。
替代性緩解措施：
1. 訊號強弱分級 —— 主動應徵權重 3、瀏覽權重 1，
   因應徵行為受曝光位置影響顯著小於瀏覽。
2. 時間衰退（λ=0.1）—— 稀釋長期累積的位置優勢，
   避免既有排序的曝光偏差在熱門度分數中無限放大。
```
