# 離線評測與 Ablation 框架

本目錄提供命題交付項目第 6 項所要求之「**有圖譜 vs 無圖譜」雙重指標 ablation script**，可一鍵重現，供評審統一執行。

---

## 一鍵重現

```bash
bash eval/reproduce.sh            # 完整 500 筆查詢
bash eval/reproduce.sh --quick    # 50 筆，快速驗證流程可跑
```

腳本會自動建立 `.venv`、安裝 `requirements.txt`、重建所有衍生資料表、產生測試集、執行 ablation。
**衍生資料不隨版控提供，一律於此重建**，避免評測依賴過期產物。

前置條件：`dataset/` 需包含主辦方提供之六份 CSV。

輸出：

| 檔案 | 內容 |
|------|------|
| `ABLATION_REPORT.md` | 指標對照表 + 評估設定 + 已知限制 |
| `ablation_results.json` | 原始指標數值（含 metadata） |
| `testset.jsonl` | 測試查詢與分級相關性標註 |

## 時序切分

主辦方於命題文件載明「工作坊將提供統一之 train/test 時序切分」，惟實際工作坊資料僅公告資料範圍 `2026-06-01 ~ 06-07`，**未公告切分日**。本專案因此採用下列自訂切分，並於此明確揭露：

```
06-01(一) 06-02(二) 06-03(三) 06-04(四) 06-05(五) │ 06-06(六) │ 06-07(日)
├──────────────── 訓練期 ────────────────────────┤           │
                                                  ├─測試查詢──┤
                                                  ├──────標註觀察窗口──────┤
```

| 期間 | 範圍 | 用途 |
|------|------|------|
| 訓練期 | `2026-06-01` ~ `2026-06-05` | 熱門度、圖譜、任何特徵僅能使用本期資料 |
| 測試查詢 | `2026-06-06` 單日 | 500 筆評測查詢之來源 |
| 標註窗口 | `2026-06-06` ~ `2026-06-07` | 僅用於觀察使用者後續行為（標準答案） |

**`06-07` 刻意不作為查詢來源**，僅保留為標註觀察窗口。若以最後一日為查詢來源，該日傍晚之搜尋將因缺乏後續行為資料而被誤標為「無相關結果」，系統性低估所有受測系統之分數。

## 相關性標註

依命題定義採分級相關性（graded relevance）：

| 等級 | 定義 |
|------|------|
| 2 | 搜尋後投遞履歷（主動應徵） |
| 1 | 搜尋後點閱職缺（職缺瀏覽） |
| 0 | 無觀察到互動 |

同一 `(query, job)` 對取最大值。

**歸因規則**：某筆行為事件歸屬於某次搜尋，若其發生於

```
[搜尋時間, min(搜尋時間 + 30 分鐘, 該使用者的下一次搜尋)]
```

以該使用者的下一次搜尋作為切點，避免將後續另一次搜尋的點擊誤算給本次；並設 2 分鐘下限，避免使用者連續修改關鍵字時窗口塌縮為零。

**僅取 `talentNo ≠ 0` 之搜尋**。匿名搜尋無法歸因行為，納入僅會產生全零標註。

### 為何不限制於 `empStr`

`userSearchLog.empStr` 記錄既有系統當次呈現之職缺清單。若將標註限制於此清單內，等同將既有排序的曝光偏差寫入標準答案 —— 受測系統即使找出一筆更適合、但既有系統從未曝光的職缺，也只會被判為不相關。

本框架因此**不限制於 `empStr`**，並於 `testset.jsonl` 記錄 `n_in_shown_head` 供偏差分析。實測結果：**標註之相關職缺僅 16.0% 出現於既有系統當次的前 20 名**，顯示曝光偏差確實顯著。

## 評估指標

實作於 `metrics.py`，含 9 項手算驗證（`python eval/metrics.py` 執行自我測試）。

| 指標 | 定義 |
|------|------|
| NDCG@10 | `DCG@10 / IDCG@10`，`DCG = Σ gain(rel_i) / log2(i+1)` |
| Hit@1 | 第 1 名是否相關（`rel > 0`） |
| Hit@10 | 前 10 名是否含任一相關職缺 |
| P@10 | 前 10 名中相關者比例，分母固定為 10 |
| MRR@10 | 第一個相關結果之排名倒數 |

**Gain 慣例**：預設 `linear`（`gain = rel`），與主辦方指定之 `pytrec_eval`／`trec_eval` 一致。
另提供 `--gain exponential`（`gain = 2^rel − 1`，LTR 文獻慣例）。**兩者不可互相比較**，報告中一律標註所採用之慣例。

無任何相關文件之查詢排除於平均之外（標準 IR 作法：此類查詢不帶訊號，僅會等比例縮放所有受測系統）。

## Ablation 組別

```bash
python eval/run_ablation.py --arms full,no_llm,graph
```

| 組別 | LLM | 語意擴展 | 圖譜 | 排序 | 用途 |
|------|-----|---------|------|------|------|
| `full` | ✓ | ✓ | ✗ | 熱門度 | 部署中之完整系統 |
| `no_llm` | ✗ | ✓ | ✗ | 熱門度 | **移除生成式 AI 之對照** |
| `no_expand` | ✓ | ✗ | ✗ | 熱門度 | 語意擴展之貢獻 |
| `graph` | ✓ | ✓ | ✓ | 圖譜 | **有圖譜之對照** |
| `no_rank` | ✓ | ✓ | ✗ | 無 | 排序階段之貢獻（對照組） |
| `no_llm_no_expand` | ✗ | ✗ | ✗ | 熱門度 | 免憑證診斷 |
| `no_llm_no_rank` | ✗ | ✓ | ✗ | 無 | 免憑證診斷 |

## 防洩漏措施

1. **熱門度表**由 `build_popularity.py` 重建，僅彙整訓練期（`06-01`~`06-05`）事件；時間衰退之參考日為訓練期最後一刻，而非資料檔最後一日。生產環境使用之 `dataset/瀏覽次數.csv`（全週）**不參與評測**。
2. **測試查詢**僅來自 `06-06`；該日及 `06-07` 之行為資料僅用於標註，不進入任何特徵。
3. **圖譜建構**依命題規定僅得使用訓練期職缺。`職缺.csv` 無上架時間欄位，故以 `職缺最後修改時間 < 2026-06-06` 作為代理條件（967,377 筆，佔 79.4%），確保所讀取之職缺文字自訓練期結束前即未再變動。
4. **`talent_no` 一律為 0**。官方 API 合約不含 `talentNo`，個人化路徑於評審評測時不會觸發；以真實 `talentNo` 評分將高估系統表現。個人化能力另以 `--use-talent` 單獨評估並分開report。

---

## 已知限制（誠實揭露）

1. **未採用 position bias correction**（IPS / Doubly Robust）。緩解措施為訊號強弱分級（應徵權重 3、瀏覽權重 1，應徵受曝光位置影響顯著小於瀏覽）與時間衰退（λ=0.1，稀釋長期累積之位置優勢）。
2. **`label = 0` 不等同不相關**。受觀察窗口長度與既有排序曝光偏差影響，實測僅 16.0% 之相關標註曾出現於既有系統前 20 名。
3. **測試查詢日為週六**，流量僅為週一之 61%，職類分布與平日不同。此為七天資料之先天限制。
4. **職缺文字之時序保真無法達成**。命題載明職缺池「含上架時間戳」，惟實際 `職缺.csv` 僅含 `職缺最後修改時間`（最新至 `2026-06-24`），無從還原任一職缺於測試日當天之文字版本。
5. **本框架之絕對數值不可與主辦方 baseline 直接比較**。標註來源、歸因窗口、查詢抽樣方式皆不同；本表之用途為**組別間之相對比較**。

## 決定性（Random Seed）

檢索與排序流程為完全確定性，不含隨機取樣、隨機初始化或隨機打散。

唯二的隨機性來源皆已固定：

| 來源 | 控制方式 |
|------|---------|
| 測試查詢抽樣（reservoir sampling）與打散 | `--seed`，預設 `42` |
| LLM 生成（Bedrock temperature 為服務端預設） | JSON schema 驗證 + 最多 3 次重試 + 規則式 fallback 收斂輸出空間；解析結果快取於 `llm_tag_cache.json`，重跑不重新生成 |

相同 seed 下 `testset.jsonl` 逐位元一致。

### 關於兩份圖譜

| 圖 | 資料範圍 | 用途 |
|---|---|---|
| `dataset/graph_cache.pkl` | 全週 06-01~06-07 | 線上服務／demo（實際服務本就該用全部資料） |

`src/graph_builder.py` 讀取事件時無日期過濾，其產出的圖包含測試日（06-06）與標註窗口（06-07）的互動，用於評測即為洩漏。且 `graph_cache.pkl` 僅存加總後的邊權重、不含時間戳，**無法事後移除測試期的邊**，只能由過濾後的事件重建。

### 分層分析

```bash
python eval/analyze_strata.py --a no_expand --b no_llm_no_expand
```

測試集查詢長度中位數僅 3 字，76% 為短關鍵字 —— 該類查詢的規則式分詞與 LLM 解析輸出完全相同，混入總平均只會將差異稀釋為零。`analyze_strata.py` 將查詢分為四層（短關鍵字／空格分隔／長字串／多職稱清單），分別報告，並以配對 bootstrap 檢定各層差異之顯著性。
